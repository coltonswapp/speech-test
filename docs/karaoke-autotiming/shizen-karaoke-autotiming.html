KA-1 through KA-7 are built on branch claude/studio-karaoke-timing-automation: schema, the aligner service on Modal (8 vCPU, 3–4 s per take), post-process and route, the Studio Auto-stamp / Mark reviewed flow, tokenizer readings with a per-line cache, the onset eval (pnpm eval:token-sync), and the generate → tokenize → align chain. Two decisions differ from the prototype described below. Shift: the shipped constant is 65 ms, anchored so stamps land about 40 ms before the RMS onset, not the 150 ms that matched one editor's tap lookback; the human-gold percentages below are therefore the prototype configuration, reproducible with --shift 150. Marks: the shipped rule takes the midpoint of the longest quiet run between the previous line's last token and the next line's first, clamped 80–250 ms before onset, because a walk-back from the onset is fooled by breaths and clicks. 2. Gold set and what the eval found

No gold files were attached locally, so I used the live public export for first-hello, which carries human tokenSync for shizuoka-tea, nine-oclock and which-mailbox. That is 48 spoken lines and 224 tokens, plus 45 human line marks read back from the m4a comment tag. new-neighbor has no tokenSync yet. The gold and prototype scripts are checked into docs/karaoke-autotiming/.

Prototype

torchaudio MMS_FA (wav2vec2 CTC, 20 ms frames), tokens romanized with pykakasi plus a small override table (三〇二 → sanmaruni, はいー → haii). One CTC pass over the whole take using the gold tokenization, then a deterministic post-process. CPU runtime is about 3 s per 40 s scene on a laptop, including model load amortized over three scenes.

Systematic biases, and how the post-process handles them

  • Raw CTC is ~150 ms late. The signed median was +158 ms across every class. Two causes stack: CTC emits a character a few frames after its acoustic onset, and human stamps are pulled 120 ms earlier than the tap by TOKEN_STAMP_LOOKBACK_SECONDS. A global −150 ms shift removes it (bias after shift: −7 ms). This constant should be re-fit whenever the aligner model or the Studio lookback changes.
  • First-of-line stamps are not a timing target. Human marks sit in the middle of the silence gap, a median 279 ms before the next speaker's onset and 331 ms after the previous speaker stops. On device those marks define per-line playback ranges, so the only requirement is "inside the gap, not clipping speech". Deriving the mark as the acoustic onset minus 80 ms (the existing SUGGESTED_BREAK_LEAD_IN_SECONDS) put 45 of 45 marks inside the gap. Placing it at the gap midpoint, clamped to 80–250 ms before onset, would match human placement more closely. Shipped: that midpoint rule, with the gap taken as the longest quiet run between the previous line's last token end and the next line's first token start (aligner bounds) rather than a walk-back from the onset, which breaths and clicks cut short: 486 of 486 marks inside the gap, median 74 ms from the human mark.
  • Single-character tokens and あ、 / え、 interjections are the weakest class (66.7% ≤100 ms). Short tokens have one or two CTC characters, so a single late frame is a large relative error. This is the class to spot-check in review.
  • Some residual error is gold noise. Of the 13 in-line tokens more than 150 ms off, four have the human stamp sitting in silence (for example それ in あ、それ私のです at +415 ms) while the aligner stamp sits at speech onset. Two are aligner mistakes where the prediction lands in silence (ありがとうございます in which-mailbox line 15). A second stamping pass by a different editor on the same scenes would tell us the human-vs-human floor; I would expect the achievable ceiling near 90% within 100 ms.
Confidence gating does not work. Per-token CTC score, romaji characters per second, and disagreement between a whole-take pass and a per-line-window pass all had roughly zero correlation with error (−0.02, −0.11, −0.01). The model is self-consistent even when it is wrong. The QA stage must therefore rely on deterministic checks plus human review, not on aligner confidence. This is the main reason v1 keeps a review pass rather than auto-publishing.

2b. The 38-scene run: the gold moves

After the first pass, 38 published scenes with human tokenSync turned out to be reachable through the public export: 524 lines and 3,105 tokens across nine collections. I re-ran the aligner on all of them with the post-process constants frozen from first-hello, so the other 35 scenes are a genuine unseen set. Alignment took 95 s total, 2.5 s per scene, with no failures and 100% token coverage.

The unseen result is clearly below the first-hello number, but the per-collection breakdown shows the reason is not mainly the aligner. Each scene's human stamps sit at a different constant offset from the audio: the per-scene signed bias runs from −203 ms (festival-day takoyaki-booth, where the aligner places nearly every token 150–400 ms earlier than the human did) to +61 ms, with a standard deviation of 54 ms across scenes. That pattern is a stamping-session effect, not a property of the audio: playback rate, output latency, and reviewer habit all shift every tap in a scene by the same amount, and the Studio fixes for 0.5× stamping (PRs 17 and 19) landed while these collections were being stamped.

Who is closer to the audio

To get a target that does not depend on any one editor, I took the 614 post-pause tokens with a clean silence of at least 150 ms before them and measured each stamp against the RMS-detected speech onset. The human stamps sit a median 95 ms before onset with a standard deviation of 155 ms; the aligner sits a median 125 ms before onset with a standard deviation of 107 ms. Scene-to-scene, the human median offset varies with a standard deviation of 63 ms, the aligner's with 20 ms. The aligner's constant lead is just the −150 ms calibration I fitted to first-hello's editor, and it can be re-fitted to the onset directly. Its consistency cannot be bought with calibration, and it is three times better than the gold's.

What this changes. "Within 100 ms of a single human" has a ceiling around 75% on this gold no matter how good the aligner is, because the gold itself disagrees with the audio by more than that from scene to scene. Two consequences: the v1 bar below is restated against acoustic onsets and a two-editor floor, and the −150 ms shift should be re-fitted so stamps land a fixed small lead (about 40 ms) before onset rather than matching one editor's reaction time. Derived line marks remain solid: 484 of 486 fell inside the silence gap on the full set.

Two more results from the full set. Lines with no in-line token more than 150 ms from the human stamp are 51.9% of 507, which would look like a poor auto-accept rate if the gold were trustworthy; against the session-drift evidence it mostly measures the gold. The stamp-in-silence heuristic flags 31.9% of tokens and catches 174 of 388 tokens more than 150 ms off, which is useful for directing review but too noisy to gate on alone. It should be tightened to post-pause tokens only, where an onset is expected.

Persisted fields

Add to the working variantTokenSyncSchema: source: "auto" | "human" | "reviewed", alignerVersion?: string, flags?: string[], and per-token optional reading?: string. On publish, carry only source through publishedTokenSyncFromWorking and publishedTokenSyncSchema so the app can distinguish reviewed from auto timing in telemetry. The Swift decoder in DialogueScenarioCollection.swift decodes fields by name and ignores extras, so adding an optional key is backwards compatible with shipped builds.

Why not construct boundaries with per-line TTS and concatenation

It stays on the list as a v2 option, but the gold shows it is not needed for boundaries: whole-take alignment recovered every speaker switch inside the silence gap, and Studio already suggests marks from VAD. Per-line synthesis also costs prosody: Gemini multi-speaker takes carry turn-taking intonation that isolated lines lose, and the first-turn voice-swap quirk noted in gemini-tts.ts would need handling per line. Revisit only if a real corpus shows overlapping speech or missing gaps.

Marginal cost is about $0.02 per scene, $0.15 per six-scene collection, and roughly $1 per curriculum unit if a unit is about five collections. At 200 scenes per month the whole pipeline is under $5. Fixed cost is the aligner service: a 1.2 GB model, warm CPU container, on the order of $10–20 per month, or near zero if run scale-to-zero with a 20 s cold start. Cost is not the constraint; editor minutes are.

Editor time today, per scene, is roughly listen-and-mark (2–3 min), tokenize (seconds), stamp about 75 tokens at real time with re-listens (6–8 min), and fixes (2–3 min): 10–14 minutes. With prefill the pass becomes a listen-through with corrections to flagged and single-character tokens, 2–4 minutes. Saving is about 8–10 minutes per scene, so a six-scene collection drops from over an hour to about 20 minutes. These are estimates from the interaction model, not measured; ticket 8 adds the timer that measures them.

5. Eval harness

Gold is any dialogue_scenario.token_sync published with source human or reviewed. The harness compares an aligner output for the same variant and contentHash. Prototype implementation is docs/karaoke-autotiming/eval_tokensync.py; ticket 6 ports it to TypeScript so it runs in CI against the DB.

Alignment policy when tokenization diverges

  • Lines are paired by index; a line whose trimmed text differs is skipped and counted as line_text_mismatch.
  • Tokens are mapped to character spans in the line text by sequential indexOf, the same rule as tokenRangesInLine. A gold token is matched when a predicted token starts at the same character offset.
  • Gold tokens whose start falls inside a predicted token count as unmatched_merged; predicted tokens starting mid-gold-token count as extra_split. Both are reported as rates, and Δ is computed only on matched tokens.
  • For end-to-end runs the pipeline's own tokenization is used, so tokenization drift shows up in coverage, not in timing. For aligner-only runs the gold tokenization is used, which isolates timing.

Metrics

  • Δ = predicted start − gold start in ms, positive is late. Report median |Δ|, p95 |Δ|, signed median (bias), and share within ±50, ±100, ±150 ms.
  • Classes: first-of-line, in-line, particle, single-character, post-pause (gold gap > 350 ms before the token), mid-phrase. First-of-line is reported but excluded from the go/no-go bar.
  • Boundary: derived line mark inside the silence gap between speakers (pass/fail), and |mark − human mark| for reference.
  • Acceptance: share of lines with no token flagged and no token beyond 150 ms, which is the proxy for lines an editor will not touch.
  • Minutes saved: measured in Studio as time from opening the take to publish, split by source.
// scripts/eval-token-sync.ts (outline)
const gold = await db.select().from(dialogueScenario)
  .where(sql`token_sync->>'source' in ('human','reviewed')`);
for (const scene of gold) {
  const variant = await loadVariant(scene.publishedVariantId);
  const pred = postProcess(await aligner.align(variant, tokensOf(scene.tokenSync)), variant);
  rows.push(...compare(pred, scene.tokenSync));   // Δ per matched token + class labels
}
print(summary(rows, { classes: ['in-line','particle','single-char','post-pause'] }));
assert(within(rows.inLine, 100) >= 0.80 && median(rows.inLine) <= 70);   // v0 bar
